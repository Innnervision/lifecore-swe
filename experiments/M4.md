# M4 — Failure-Aware Graph & Negative Experience Learning

## 1. Research Question
**"Can verified negative experience improve software-engineering agent navigation by reducing repeated transitions and hypotheses associated with previously verified failures?"**

Milestone M3 established that verified positive experience acts as an effective structural prior over repository graph transitions, accelerating localization and enabling the code graph to serve as a compact topological memory. Milestone M4 investigates the complementary question:

**Can negative experience become a structural anti-prior?**

When software engineering agents navigate large codebases, they frequently fall into recurring failure modes: chasing similarly named helper modules, adopting plausible but invalid hypotheses, confusing callers and callees, and repeating historically disproven navigation paths across related tasks. M4 explores whether structured, causally attributed failure records can be used as a controlled negative signal in edge scoring to suppress unproductive transitions while strictly preserving valid alternative paths.

---

## 2. Hypothesis
1. **Structural Anti-Prior Hypothesis**: Verified failure evidence can reduce the probability of repeatedly following demonstrably unproductive repository transitions (demoting trap edges), while preserving alternative paths necessary for successful repair.
2. **Attribution Selectivity Hypothesis**: Negative penalties must be applied *selectively* based on strict causal attribution (`STRONG` or `VERIFIED`). Indiscriminate edge penalization across all visited or modified edges will cause catastrophic over-pruning (high `false_negative_guidance_rate`) and degrade agent performance.
3. **Safety & Floor Protection Hypothesis**: Enforcing a strict score floor ($\text{score\_floor} = 0.15$) and bounding negative penalties prevents graph disconnection, ensuring that an edge is never deleted solely due to historical failures and alternative recovery routes remain discoverable.
4. **Structural Memory Hypothesis (Condition E)**: Structural edge penalties in the code graph alone, without narrative textual failure explanations injected into the prompt, provide sufficient negative guidance to deter repeated mistakes while reducing prompt token consumption and inference latency.

---

## 3. Motivation from M3
While M3 successfully demonstrated that verified successes reinforce structural paths, it revealed an asymmetry in agent navigation:
1. **Trap Vulnerability**: When presented with tasks involving deceptive module structures (e.g., `storage/cache.py` vs. `storage/buffer.py`), positive priors for neighboring functions were insufficient to prevent the agent from repeatedly choosing seductive but incorrect transitions.
2. **Repeated Hypotheses**: In multi-step or sequential tasks, when an agent formed an incorrect hypothesis (such as implementing a global dictionary wipe instead of per-client isolation), it had no mechanism to remember that this transition had already been disproven by test assertions.
3. **Over-Pruning Dilemma**: In software repositories, a failed task often contains 90% valid navigation and only 10% faulty logic. If an entire trajectory is marked negative, valid structural pathways risk being poisoned. M4 solves this through causal attribution and safe edge scoring.

---

## 4. Failure Taxonomy
M4 rejects collapsing all failures into a single category. Failures are classified into 10 distinct types with dedicated handling rules:

| Failure Type | Definition | Causal Graph Impact |
|:---|:---|:---|
| **NAVIGATION_FAILURE** | Agent traversed irrelevant directory or file branches. | Eligible for transition penalty only if unproductiveness is verified. |
| **LOCALIZATION_FAILURE** | Agent inspected files but failed to identify the target defect site. | Demotes incident reference edges if an unequivocal distractor is proven. |
| **HYPOTHESIS_FAILURE** | Agent formed a specific semantic assumption that proved false. | Penalizes edges representing the disproven implementation assumption. |
| **PATCH_FAILURE** | Syntax or indentation errors preventing compilation/execution. | **No graph edge penalty** (syntactic issue, not structural invalidity). |
| **TEST_FAILURE** | Targeted test failed with an `AssertionError` or unexpected exception. | **Strongly eligible** if modified symbol directly generated the failure traceback. |
| **VERIFICATION_FAILURE** | Independent verifier failed (e.g. unintended files touched, regression). | Penalizes boundary-escaping transitions that touched out-of-scope files. |
| **STALE_INFORMATION** | Code changed since previous observation, invalidating assumptions. | **No penalty applied to source graph**; marks memory stale. |
| **TOOL_FAILURE** | Tool call execution error (filesystem permission, bad arguments). | **No graph edge penalty** (operational error, not code architecture). |
| **BUDGET_EXHAUSTION** | Agent reached max loop iterations without converging. | Attributed as `NONE`; stores trajectory evidence without graph penalties. |
| **OTHER** | Unclassified anomaly or execution termination. | Preserved for telemetry; unpenalizable. |

## 5. Negative Experience Model
Negative experiences are modeled as first-class episodic records persisted in a dedicated SQLite-backed overlay (`m4_negative_overlay.db`):

```python
class NegativeExperienceRecord:
    experience_id: str
    task_id: str
    repository_id: str
    repository_version: str
    task_category: str
    failure_type: str
    failed_hypothesis: str
    failed_action: str
    failed_transition: Optional[str]
    source_node: str
    target_node: str
    edge_type: str
    failure_reason: str
    failed_test: str
    expected_behavior: str
    observed_behavior: str
    confidence: float
    timestamp: float
    provenance: Dict[str, Any]
    attribution_strength: str
    attribution_reason: str
    stale_status: str
    file_hashes: Dict[str, str]
```

### Attribution Levels
- **NONE**: No clear causal link to a structural transition (e.g. loop iteration timeout with no edits).
- **WEAK**: Incidental traversal without modification.
- **MODERATE**: File modified but test assertion failure occurred elsewhere in unrelated code.
- **STRONG**: Modified symbol or transition explicitly referenced in test traceback / assertion failure.
- **VERIFIED**: Direct causal reproduction where modifying the symbol produced an explicit regression.

**Scientific Control Rule**: Only **STRONG** and **VERIFIED** attribution records are eligible for graph edge penalties. All others are stored for telemetry but apply zero penalty ($\Delta_{\text{neg}} = 0.0$).

---

## 6. Attribution Mechanism
The `FailureAttributor` engine inspects the post-task state to determine causal attribution:
1. **Traceback Analysis**: Regular expressions extract symbols mentioned in test assertions, exceptions, and stack traces.
2. **AST Intersection**: Matches traceback symbols against modified nodes in the repository graph index (`GraphIndex.find_by_path`).
3. **Transition Isolation**: Maps the failed symbol back to specific incoming `CALLS`, `TESTS`, and `DEFINES` edges.
4. **Attribution Strength Assignment**:
   - If a test assertion specifically failed on a function modified by the agent: `STRONG` or `VERIFIED`.
   - If the agent's explicit hypothesis assumed an invalid semantic contract: `STRONG`.
   - If the agent ran out of turns without editing the code: `BUDGET_EXHAUSTION` with attribution `NONE`.

---

## 7. Negative Edge Scoring
The edge score combines static base weight, positive experience boost, and negative experience penalty:

$$\text{final\_edge\_score} = \max\left(\text{score\_floor},\; S_{\text{base}} + \Delta_{\text{pos}} - \Delta_{\text{neg}}\right)$$

The negative experience penalty $\Delta_{\text{neg}}$ is computed deterministically:

$$\Delta_{\text{neg}} = \beta_{\text{neg}} \times N_{\text{factor}} \times A_{\text{attrib}} \times R_{\text{task}} \times F_{\text{fresh}} \times D_{\text{recency}} \times C_{\text{conf}}$$

### Coefficient Definitions & Empirical Calibration:
- $\beta_{\text{neg}} = 0.80$: Base scaling coefficient for negative penalties.
- $N_{\text{factor}} = \frac{N_{\text{fail}}}{1 + N_{\text{fail}}}$: Bounded sub-linear frequency scaling ($N=1 \to 0.50$, $N=5 \to 0.83$, $N \to \infty \to 1.0$).
- $A_{\text{attrib}}$: Attribution strength multiplier:
  - $\text{VERIFIED} \to 1.00$
  - $\text{STRONG} \to 0.80$
  - $\text{MODERATE} / \text{WEAK} / \text{NONE} \to 0.00$ (with attribution filtering enabled)
- $R_{\text{task}} = \text{task\_relevance} \in [0.1, 1.0]$: Jaccard overlap between task intent tokens and target symbols/files. Ensures failures in `rate_limiter` do not penalize `crypto` or `storage` tasks.
- $F_{\text{fresh}} \in \{0.30, 1.0\}$: Freshness validation. If code has been modified since the failure occurred, the penalty is dampened ($0.30$).
- $D_{\text{recency}} = \max\left(0.60, \exp\left(-\frac{\Delta t}{\tau_{\text{neg}}}\right)\right)$: Exponential temporal decay with half-life $\tau_{\text{neg}} = 86400\,\text{s}$ (24 hours).
- $C_{\text{conf}} = \max(0.5, \min(1.0, \text{confidence}))$: Confidence factor of the negative record.

## 8. Safety Against Over-Pruning
A primary risk in negative experience systems is **over-pruning**: completely eliminating an edge that might be needed as an alternative path or fallback.

M4 enforces two foundational safety rules:
1. **No Edge Deletion**: Negative experience **never removes an edge** from the graph. It only adjusts ranking priority.
2. **Configurable Score Floor**: The score is strictly bounded from below:
   $$\text{final\_edge\_score} \ge \text{score\_floor} = 0.15$$
   Even an edge with 10 verified failures cannot drop below $0.15$. Unpenalized alternative edges ($S_{\text{base}} \ge 0.50$) will always be selected first, but if no other path exists, the agent can still traverse the penalized edge.

---

## 9. Positive + Negative Interaction
When an edge has both historical successes and historical failures, M4 balances evidence:
- **5 Successes + 1 Failure**:
  - $\Delta_{\text{pos}} = 1.0 \times \frac{5}{6} \times R = +0.83 R$
  - $\Delta_{\text{neg}} = 0.80 \times \frac{1}{2} \times 0.80 \times R = -0.32 R$
  - $\text{Net} = +0.51 R > 0$ (Edge remains net positive; one mistake does not erase solid history).
- **1 Success + 5 Failures**:
  - $\Delta_{\text{pos}} = 1.0 \times \frac{1}{2} \times R = +0.50 R$
  - $\Delta_{\text{neg}} = 0.80 \times \frac{5}{6} \times 1.00 \times R = -0.67 R$
  - $\text{Net} = -0.17 R < 0$ (Edge becomes net negative; consistent failures overcome one anomalous success).

## 10. Controlled Failure Benchmark
The benchmark consists of 4 diagnostic tasks executed on `hydra_mesh` (`fixtures/scaled_repo`), designed to replicate the primary software engineering failure traps:

1. **M4-TASK-A (Deceptive Sibling Module / Buffer vs. Cache)**:
   - *Target*: `hydra_mesh/storage/buffer.py::RingBuffer.push` (off-by-one capacity check).
   - *Trap*: `hydra_mesh/storage/cache.py` has similar key-value eviction methods.
   - *Phase 1 Trap*: Without negative guidance, agent navigates to `cache.py`, modifying `KeyValueCache`, failing `test_buffer_push_and_capacity`.
2. **M4-TASK-B (Caller vs. Callee Ambiguity / Transformer DLQ Routing)**:
   - *Target*: `hydra_mesh/pipeline/transformer.py` (route missing event schema to DLQ).
   - *Trap*: `hydra_mesh/pipeline/dead_letter.py` (modifying DLQ implementation).
   - *Phase 1 Trap*: Agent edits `dead_letter.py` directly, causing schema errors to persist in caller.
3. **M4-TASK-C (Disproven Hypothesis / Multi-Client Isolation Trap)**:
   - *Target*: `hydra_mesh/ingest/rate_limiter.py::SlidingWindowLimiter.reset(client_id)`.
   - *Trap*: Naive global wipe (`self.history = {}`) when `client_id` is supplied.
   - *Phase 1 Trap*: Agent adopts global wipe hypothesis, breaking multi-client quota isolation.
4. **M4-TASK-D (Temptation Avoidance / Subsequent Related Task)**:
   - *Target*: `hydra_mesh/ingest/rate_limiter.py::SlidingWindowLimiter.allow_request` (burst allowance).
   - *Temptation*: Distractor transitions in neighboring modules.
   - *Evaluation*: Verifies whether negative experience prevents repeated exploration of penalized paths.

## 11. Experimental Conditions
Five core conditions were evaluated using real Gemma 4 (`models/gemma-4-26b-a4b-it`):
- **Condition A (STATELESS)**: Gemma + standard filesystem tools, no code graph, no persistent memory.
- **Condition B (STATIC GRAPH)**: Gemma + M1C deterministic AST code graph, no experience memory.
- **Condition C (POSITIVE GRAPH)**: Gemma + M3 experience-conditioned graph, positive experience only.
- **Condition D (POSITIVE + NEGATIVE GRAPH)**: Gemma + positive priors + negative experience penalties.
- **Condition E (POSITIVE + NEGATIVE GRAPH, NO RAW TEXT)**: Same as D, with zero textual failure narrative injected into the LLM prompt. The structural graph is the sole memory medium.

Ablations:
- **Ablation 1 (NO ATTRIBUTION FILTERING)**: Condition D with attribution filtering disabled (all visited edges penalized).
- **Ablation 2 (NO RECENCY DECAY)**: Condition D with recency decay disabled ($\tau_{\text{neg}} = 10^9\,\text{s}$).

## 15. Condition E Findings: Structural Anti-Prior vs. Narrative Text
In Condition E (`POSITIVE_NEGATIVE_NO_TEXT`), the agent received **zero raw failure narrative text**. The structural edge penalties alone modulated graph ranking.
- **Success Rate**: 100.0% (4/4 tasks solved).
- **Search Count**: **0.00 searches** across all tasks (graph provided immediate, high-precision localization).
- **Tool Calls**: 6.00 calls (comparable to Condition D's 5.75).
- **Significance**: Confirms that structural graph penalties function as an independent, language-model-agnostic memory mechanism. Narrative text is not required for negative avoidance if graph topology is properly weighted.
